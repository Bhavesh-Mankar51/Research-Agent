Composio · AI Product Ops Intern Integration research agent

Detailed analysis

An agent that reads an app's developer docs and returns an evidence-backed verdict on whether you could build a toolkit for it today. This page reports what it actually produced — including the runs that failed and the number that started at 50%.

Built 17–18 Aug 2026 LangGraph · Composio · Claude Opus 5 + Haiku 4.5 $2.48 of model spend

Note: the sample is 6 apps, not 100

The assignment supplies 100 apps. This page reports 6. The agent, the batch runner, the verification loops and the accuracy audit are all real and all ran — but the Anthropic account ran out of credits mid-batch, and four of the five apps in the final pass died on "credit balance is too low" rather than on anything the agent did.

Nothing here is extrapolated to fill the gap. There are no invented rows, no estimated verdicts, and no patterns claimed at a confidence the sample cannot carry. What follows is 6 apps of real output, hand-checked field by field against vendor documentation. Scaling to 100 is a billing problem, not an engineering one: the runner is written, tested, and takes an app list as an argument.

The headline

What the sample shows

3 / 6 ship an official MCP server — Salesforce, Linear, Stripe
4 / 6 self-serve: credentials without talking to anyone
1 / 6 hard-gated behind contact-sales (PitchBook)
0 fabricated citations or false claims, across every run

Four patterns held across the six. They are stated as observations on a six-app sample, because that is what they are.

  • Auth is not the blocker anyone expects. Every app in the sample has a documented, obtainable credential path — OAuth2 for the CRM and support tools, plain API keys for the developer-facing ones. Not one of them is blocked on auth.
  • The real gate is production access, not first access. WhatsApp Business hands you a token and a test number in minutes, then requires business verification before you can message a real customer. The friction sits after the demo works, which is exactly where a toolkit build discovers it.
  • Commercial gating is a category property, not a technical one. PitchBook's API is REST and perfectly ordinary; it is simply sold, not published. The only route in is a lead form. That is a correct finding, not a research failure.
  • Official MCP is already table stakes at the top end. Half the sample ships a vendor-hosted MCP server. This was also the single dimension the agent was worst at detecting — it scored 1 / 6 on MCP before the fixes below.

The agent

What was built

One app name in, one evidence-backed report out. Planning is deterministic Python rather than an LLM call — the six dimensions are fixed by the problem, so decomposing into lanes costs zero tokens and cannot hallucinate a lane.

Lanes are the cost control

Each lane returns a handful of structured claims; raw page text never reaches the orchestrator. The expensive model's context scales with claims made, not pages read — which is what makes Opus affordable on synthesis.

Citations are checked in Python

Every URL a tool returned is recorded. Any cited URL outside that set is flagged deterministically and fails verification, whatever the critic model thought. Across every run on this page, that check fired zero times.

Unknown is a first-class answer

Every enum has an unknown member and confidence is recorded per dimension. This is why the agent's failure mode is silence rather than invention — see the audit.

The verification

50% on the first pass, and why

Six apps were scored across six dimensions each — 36 field-level judgements — against documentation read by hand. The first pass got 18 of 36 right: 50%.

The shape of those 18 misses matters more than the number. Seventeen were abstentions — the agent returned unknown where a documented answer existed. One was an under-confident verdict (Linear called buildable_with_friction; it is buildable today). None was a false statement, and none cited a URL that was never fetched. The agent was not lying. It could not reach the documentation, and it said so.

Then the reason for all that silence turned out to be four defects in the harness, not the model.

Root cause

Four defects, found by reading the logs

01

Three of four toolkits were dead, and the agent could not tell

Composio's tools.get() returns tool schemas whether or not the user has connected the toolkit. EXA, Firecrawl and Tavily had no connected account, so 16 of 36 bound tools returned 404 the moment they were called — after the model had already spent a turn choosing them. The provider reported toolkits_skipped: {}, because nothing had thrown.

Fix — check each toolkit's auth mode and the live connected accounts at discovery. Anything needing credentials it does not have is skipped and named in the run record instead of silently bound.
02

Failed calls were charged to the search budget

Each lane gets a fixed number of tool calls. Failures were counted against it, so a lane could spend its entire budget on 404s and return nothing at all. PitchBook's report said it plainly: "All research lanes returned no findings."

Fix — only calls that returned something count. A call that errored produced no evidence and must not starve the lane of its attempts.
03

The worker was offered Amazon, Flights and Hotels search

The tool filter admitted any slug containing SEARCH — and COMPOSIO_SEARCH prefixes every one of its verticals, so flight, hotel, shopping and TripAdvisor search were all bound to a lane researching API auth. Every one cost input tokens on every turn and offered a plausible wrong choice.

Fix — exclude the consumer verticals. 36 tools became 7.
04

One over-long paragraph destroyed the entire report

The worst of the four. integration_notes caps at 800 characters; given richer findings, Opus wrote about a thousand. LangChain's structured output turns a schema breach into a returned parsing_error rather than an exception, and the code discarded it — so every lane's work was thrown away and the run reported only "Synthesis returned no structured report." Four of five runs in the second pass died this way. The same all-or-nothing flaw sat in the lane parser: a single 900-character quote discarded all seven of Stripe's findings, including the one that had correctly found mcp.stripe.com.

Fix — log the parse error, then salvage deterministically: trim only the fields that breached a length cap and re-validate. Findings are salvaged one at a time, so one bad quote can no longer cost six good claims. Only length violations are repaired — any other error means something substantive is wrong, which is not ours to paper over.

What the fixes bought — and what is still unproven

The rerun is where honesty costs something. Stripe went from 5 / 6 to 6 / 6: it found mcp.stripe.com and labelled it official, moved API breadth from unknown to broad, and raised every confidence rating to high. Tool calls per run rose from 8 to 15 and distinct URLs seen from 71 to 307 — the agent could finally read.

Then the credits ran out. Stripe is the only app that completed the fixed pipeline. The other four returned "credit balance is too low". So the improvement is measured on a sample of one, and this page will not call that a validated 100% until the other five have run. The defects are real and fixed, and 41 tests pass — but one app is one app.

Worth noting on the other side: even at 6 / 6, the critic still raised six issues against the Stripe report — an unsourced webhooks aside, and an endpoint count resting on an unvetted third-party aggregator. The verification layer is doing its job on output that a human would otherwise have waved through.

The human

Where a person was needed

  • Diagnosing. The agent honestly reported low confidence on nearly everything. It could not work out why — that its own tools were returning 404s. That took a person reading warning logs the agent never saw.
  • Telling "unknown" apart from "gated." The agent said unknown for PitchBook. The correct answer — contact-sales, blocked, with the lead form as evidence — required a person deciding that absence of public docs is the finding.
  • Ground truth. All 36 field judgements were made by opening vendor documentation in a browser. An agent grading its own homework is not an accuracy check.
  • Calling the schema trade-off. Deciding that a length breach should be trimmed rather than fatal — and that only length breaches should be — is a judgement about which errors are cosmetic. That is not a call to leave to a retry loop.
Honesty

What defeated us

Anthropic credits

The hard stop. Ran out during the final pass and took four of five apps with it. Every "failed" row on this page traces to billing, not to agent logic.

Composio connections

Only COMPOSIO_SEARCH was ever connected, and it needs no credentials. The whole exercise ran on search plus URL fetch, with no real scraping toolkit. Connecting Firecrawl or Exa is the single highest-value next step.

PitchBook

Defeated the agent completely on the first pass — zero findings, every field unknown. A human got the answer in two minutes. Private docs are a genuinely hard target for a search-only agent, because there is nothing to find.

MCP detection

The weakest dimension by far: 1 / 6 before the fixes. MCP servers are announced in changelogs and separate docs trees that a docs-focused search does not surface unless it is told to look.
